# Terraform — VMs on Proxmox

Stage 2 of the pipeline: clones the Packer-built template into VMs. Terraform
owns only the VM's **existence and shape** — CPU, memory, disk, network, and the
cloud-init user/SSH key. Everything running inside the VM is Ansible's job.

See the [root README](../README.md) for how the stages fit together.

## Layout

```txt
terraform/
├── modules/
│   └── base-vm/          # reusable: clone a template into a cloud-init VM
└── projects/
    ├── k3s/              # k3s VM        (TFC workspace: k3s)
    ├── monitoring/       # Monitoring VM (TFC workspace: Monitoring)
    └── nextcloud/        # Nextcloud VM  (TFC workspace: Nextcloud)
```

**One project = one VM = one Terraform Cloud workspace = one state file.**
Projects are deliberately not combined into a single root module: a `terraform
apply` for Nextcloud should never be able to touch the k3s VM, and each can be
destroyed and rebuilt on its own.

Projects are thin. A project supplies variables and a provider block, and
delegates the actual resource to `modules/base-vm`:

```hcl
module "nextcloud" {
  source        = "../../modules/base-vm"
  vm_name       = var.vm_name
  template_name = var.template_name
  cpu_cores     = var.cpu_cores
  # ...
  ssh_public_key = file(pathexpand(var.ssh_public_key))
}
```

Per-directory input/output tables are generated by `terraform-docs`:

- [projects/nextcloud/README.md](projects/nextcloud/README.md)
- [projects/monitoring/README.md](projects/monitoring/README.md)
- [projects/k3s/README.md](projects/k3s/README.md)
- [modules/base-vm/README.md](modules/base-vm/README.md)

### Generating Ansible inventory

A project may also write its own Ansible inventory fragment — `monitoring` does,
via a `local_file` resource rendering `templates/inventory.yml.tftpl` into
`ansible/inventory/monitoring.yml`.

`ansible/inventory/` is a **directory** inventory, so fragments merge rather
than overwrite: each project owns exactly one file and cannot clobber another
project's hosts. `inventory/group_vars/` is hand-authored and is never written
from Terraform — addresses are machine state, tuning is not.

The generated fragments are git-ignored, and the inventory host name is
deliberately different from `vm_name` (`monitoring-vm` vs `monitoring`), since
Ansible warns when a host and a group share a name.

## Prerequisites

- **Terraform 1.15.7** — `make install-binaries` from the repo root.
- **A Packer-built template** on the Proxmox node (see
  [../packer/README.md](../packer/README.md)); its name goes in
  `template_name`.
- **A `terraform@pve` API token** (below).
- **Terraform Cloud** — `terraform login`, and the workspace set to **Local**
  execution (below).

## Usage

Always run from inside a project directory:

```bash
cd projects/nextcloud                    # direnv exports TF_VAR_* on the way in
terraform init
terraform plan
terraform apply
terraform output ansible_inventory_line  # paste into ansible/inventory
```

No `terraform.tfvars` is needed. `terraform/.envrc` supplies
`TF_VAR_pm_api_url`, `TF_VAR_pm_api_token_id`, `TF_VAR_pm_api_token_secret` and
`TF_VAR_pm_tls_insecure` from the repo-root `secrets.yaml` — one `.envrc` covers
every project, because direnv walks *up* from the working directory to find it.
Every other variable has a default in `variables.tf`. See
[Secrets](../README.md#secrets).

`terraform.tfvars` stays git-ignored (`*.tfvars`) and still wins over the
environment if you create one; `terraform.tfvars.example` now documents only the
**non-secret** overrides.

To tear a VM down: `terraform destroy` in that project only. The Packer
template is untouched — it is not managed by Terraform.

### Adding a new project

1. `mkdir projects/<name>` and copy `main.tf`, `variables.tf`, `outputs.tf`,
   `versions.tf`, and `terraform.tfvars.example` from `projects/nextcloud`.
2. In `versions.tf`, change the `workspaces { name = … }` to a **new** TFC
   workspace name, and create that workspace in the `colac_homelab` org.
3. Set the workspace to **Local** execution mode (below).
4. Adjust sizing defaults in `variables.tf`, then `terraform init && apply`.
5. Run `terraform-docs markdown table --output-file README.md .` (pre-commit
   does this automatically).

## Terraform Cloud

State lives in Terraform Cloud (org `colac_homelab`), but **execution must be
local**: Proxmox is on the LAN and unreachable from TFC's runners, and remote
runs also can't read the relative `../../modules` source path.

Set it per workspace:
[Terraform Cloud](https://app.terraform.io/app/) → Workspace → Settings →
Execution Mode → **Local**.

Symptoms of forgetting: a run that fails to reach the Proxmox API, or a
`module not found` error for `../../modules/base-vm`.

## What `base-vm` does

Wraps a single `proxmox_vm_qemu` resource with the settings that make a
Packer template clone reliably:

- **`full_clone = true`** — an independent copy, not a linked clone.
- **`boot = "order=scsi0"`** — boots the cloned OS disk, not the cloud-init
  drive or the network.
- **`scsihw = "virtio-scsi-single"`** — must match what the template was built
  with, or the disk isn't found.
- **cloud-init** — `ciuser` + `sshkeys` only. This is the one place cloud-init
  is used, and only for login access; app config is Ansible's.
- **`agent = 1`** — the QEMU guest agent is what lets Terraform report the
  VM's DHCP-assigned IP as an output.

Outputs: `vm_name`, `vm_ip`, and `ansible_inventory_line` — a ready-to-paste
line for `ansible/inventory/hosts.yml`.

## Gotchas

- **Disk size can only grow.** `disk0_size` must be **≥** the template's disk.
  The Telmate provider cannot shrink a cloned disk; instead of failing, it
  silently creates a new empty one and the VM boots to nothing.
- **The provider pin is load-bearing.** `Telmate/proxmox 3.0.2-rc07` is pinned
  in every `versions.tf`; mixing versions across projects breaks `terraform
  init` against the shared lock files. Don't bump it casually.
- **TLS verification is on** (`pm_tls_insecure = false`) because the Proxmox
  host has a valid certificate for its hostname — which only resolves through
  PiHole. Keep PiHole as your DNS while running Terraform.
- **No IP is assigned by Terraform.** VMs take DHCP; give anything long-lived a
  DHCP reservation so its address doesn't move under Ansible's inventory.

## Create the Terraform user in Proxmox

Run in the Proxmox node console:

```bash
# create role and set privileges
pveum role add TerraformRole -privs "Datastore.AllocateSpace Datastore.AllocateTemplate Datastore.Audit Pool.Allocate Pool.Audit Sys.Audit Sys.Console Sys.Modify VM.Allocate VM.Audit VM.Clone VM.Config.CDROM VM.Config.Cloudinit VM.Config.CPU VM.Config.Disk VM.Config.HWType VM.Config.Memory VM.Config.Network VM.Config.Options VM.Migrate VM.PowerMgmt VM.GuestAgent.Audit SDN.Use"

# create user (choose your own password)
pveum user add terraform@pve --password 'CHANGE_ME'

# set permissions
pveum aclmod / -user terraform@pve -role TerraformRole

# create API token — prints the secret exactly once
pveum user token add terraform@pve terraform-automation --privsep 0
```

The token ID and secret go in the repo-root `secrets.yaml` as
`proxmox_terraform_token_id` / `proxmox_terraform_token_secret`
(`sops secrets.yaml`). `terraform/.envrc` maps them to `TF_VAR_pm_api_token_id`
/ `TF_VAR_pm_api_token_secret`. Note this is a *different* token from Packer's:
Packer needs template-build rights, Terraform needs clone/configure rights, and
neither should carry the other's.
